# 04 · 授权防篡改（以及不该做的事）

## 先说结论

**客户端的一切判断都可以被绕过。** 这不是技术不够好，而是数学事实：
二进制在用户机器上，他有 root/调试器/改机工具，就能改内存、改分支、改返回值。

所以真正的原则只有一条：

> 客户端校验决定「**要不要显示入口**」，
> 服务端校验决定「**要不要给数据**」。

如果你的付费功能完全离线可用、服务端不参与，那它必然可被破解。
反过来说，只要付费价值来自服务端（云同步、AI 额度、内容库、导出高清文件），
破解成本就会陡增 —— 因为攻击者得伪造你的服务端，而不只是改个 `if`。

## 分层防线（按性价比排序）

### 第 1 层：服务端权威（必做）

- 客户端请求付费内容时带上令牌，服务端每次校验
- 令牌短 TTL（本项目默认 24 小时），到期必须回来换
- 服务端不信任客户端传来的"我是 Pro"，只信自己算出来的权益

```bash
# 客户端：GET /v1/me  Authorization: Bearer <token>
# 服务端：验签 + 查权益 + 才返回付费内容
```

### 第 2 层：交易凭据校验（必做）

- Apple：App Store Server API 查 `transactionId`，或本地验 JWS 签名
- Google：Developer API 查 `purchaseToken`
- 关键：**不要只信客户端本地拿到的凭据内容**，要验签

### 第 3 层：提高破解成本（选做，别过度）

| 手段 | 效果 | 代价 |
|---|---|---|
| 代码混淆 / Swift 符号剥离 | 增加逆向阅读成本 | 崩溃日志难读 |
| 关键逻辑放服务端 | 显著 | 需要联网 |
| 反调试（`PT_DENY_ATTACH`） | 挡住初学者 | 会误伤测试与合法调试 |
| 越狱检测 | 心理威慑 | **误伤大量正常用户**（越狱≠盗版） |
| 证书固定（pinning） | 挡中间人抓包 | 证书轮换会导致全量用户失联，运维要跟上 |

经验值：**前两层做到位，收益占 80%**；第三层是"让对方多花半小时"，不是安全边界。

### 第 4 层：风控信号（有规模后做）

- 同一账号短时间内出现在多个地区/过多设备
- 退款率异常高的账号
- 同一 `transactionId` 被多个账号使用（家庭共享滥用）

命中后不是直接封，而是**降级 + 人工复核**，避免误杀付费用户。

## 常见的错误设计

```swift
// ❌ 把判断写死在客户端
var isPro: Bool { UserDefaults.standard.bool(forKey: "pro") }
// 攻击者一行命令就能改

// ❌ 付费内容随包下发，只是 UI 藏起来
// 解包就能拿到全部素材

// ❌ 用可预测的值做"授权码"
if code == "ABC-123" { unlock() }

// ❌ 硬编码密钥在客户端
let secret = "sk_live_xxx"   // 反编译直接读走
```

## 关于"删除/绕过别人 App 的购买校验"

这件事我不做，也说清楚为什么它对你没好处：

- 法律上属于绕过技术保护措施，分发工具可能承担侵权责任
- 你在 App Store / Google Play 上架时，任何"破解/去广告他人应用"的功能都会被拒审
- 你自己的 App 一旦被同样手段破解，你希望别人说"这只是学习"吗

**有正当需求的对应做法**：

| 你可能想做的 | 正当实现 |
|---|---|
| 我自己的 App 想做个免费版（无会员功能） | 加一个 `free` 商品目录 / 编译开关，正常发版 |
| 测试时想模拟"已购买"状态 | 用 StoreKit Testing（`.storekit` 配置文件）或本项目的 mock 事件 |
| 想在越狱设备上调试自己的 App | 正常签名调试即可，不需要绕自己的校验 |
| 想研究别人 App 的内购实现 | 读它的公开 SDK 源码、官方文档，或看我列的参考仓库 |

## 自测清单

上线前逐条过一遍：

- [ ] 断网启动，付费用户是否仍能用（离线令牌）
- [ ] 令牌过期后，是否优雅提示而不是直接崩溃
- [ ] 改系统时间能不能骗过到期判断（服务端时间为准）
- [ ] 退款后，付费内容是否在下一次请求就被拒
- [ ] 同一账号两台设备是否都能用（`Transaction.currentEntitlements`）
- [ ] 付费用户是否真的不再请求广告 SDK
- [ ] 客服能不能手动补授权（后台工具，别靠改数据库）

# 01 · 授权模型设计

做会员/内购最容易犯的错，是把「商品」和「功能」直接绑死：

```js
// ❌ 反面教材：以后加个促销包、涨价、搞捆绑，全都要改
if (user.bought === 'pro.monthly') showProFeatures();
```

正确做法是中间加一层**权益（Entitlement）**：

```
用户 ──购买──> 商品(Product) ──解锁──> 权益(Entitlement) ──控制──> 功能
                  pro.monthly            ad_free             去广告
                  pro.yearly             pro_features        高级功能
                  pro.lifetime           cloud_sync          云同步
                  adfree.lifetime
```

客户端只问一句 `has('ad_free')`，至于这个权益是月订阅、年订阅还是买断给的，它不需要知道。
好处很直接：换价格、加商品、做限时捆绑包，客户端**一行都不用改**。

## 四个核心对象

| 对象 | 说明 | 存在哪 |
|---|---|---|
| Product | 售卖单元，含周期和它解锁的权益 | 配置文件 + 商店后台 |
| Purchase | 一次交易记录（含到期时间、状态） | 服务端数据库 |
| Entitlement | 用户"当前拥有的能力"，是算出来的 | 不落库，每次由 Purchase 推导 |
| Event | 平台通知（购买/续订/退款…） | 事件表，可回溯 |

关键点：**Entitlement 不存库**。存了就会有一堆"库里的过期时间和真实时间不一致"的脏数据。
它应该是 `f(所有 Purchase, 当前时间)` 的纯函数结果 —— 本项目就是这么实现的（`src/entitlement.js`）。

## 状态机

```
                purchase
      (无) ──────────────> active ────renew────> active（到期时间往后推）
                            │  │
                  cancel    │  │  refund / revoke
              ┌─────────────┘  └──────────────> refunded / revoked（立即失效）
              ▼
          canceled ──(到期)──> expired
              │
          active ──(到期未续订)──> 宽限期 ──(仍未扣款)──> expired
```

四条规则值得记住：

1. **cancel 不等于立即失效**。用户只是关了自动续订，已经付过钱的周期要让他用完。
2. **宽限期只给"还在自动续订"的订阅**。扣款失败（卡过期、余额不足）时，商店会重试几天，
   这期间属于正常用户，不该断他服务。已取消的订阅不享受宽限期。
3. **退款和撤销是立即失效**，且**不给宽限期**。
4. **买断（lifetime）没有到期时间**，`expiresAt = null`，永远 `granted`。

## 多个商品解锁同一权益怎么办

用户可能同时有 `pro.monthly`（快到期）和 `adfree.lifetime`（永久）。
解析时取「最宽松」的那个：永久 > 到期晚 > 宽限期内。

本项目的实现是给状态打优先级（`rank()`），而不是简单取第一个 —— 否则数组顺序一变，
用户就可能突然"失去"已经买断的权益。

## 时间必须可注入

```js
new EntitlementService({ clock: () => Date.now() })
```

生产用系统时间，测试里传固定时间戳，就能瞬间验证「三个月后会不会过期」，
而不用真的等三个月。
